# 代码调研（Investigate → Plan）

目标：**在改动前用最少的 token 找到正确的落点，并给出最小改动方案。**

本 Skill 只负责「怎么找、找到什么程度停、最后输出什么」。具体检索能力由环境提供的工具承担（文件搜索、AST/符号搜索、代码图谱、文件读取、终端）；不要假设某条命令一定存在，也不要在本 Skill 里重复实现工具用法。

## 何时使用
- 需求已明确，但不知道实现落在哪个文件/函数。
- 要改共享逻辑，需先确认有哪些调用点。
- 接手陌生模块、评估影响面、判断改动是否外溢。
- 用户说「先看看代码」「分析一下再改」。

## 何时跳过
- 明确的一行改动、改名、拼写或文案修正：直接改。
- 目标文件已在上下文中读过：直接改。
- 纯问答/解释：按需检索即可，不必产出改动方案。

## 检索阶梯（成本从低到高，够用就停）

1. **定位文件**：用文件名/路径模式搜索（glob 类工具）。只有确定层级时才列目录，禁止递归列举整个仓库。
2. **定位行**：用内容搜索（grep / ripgrep 类工具），一次带上 include 过滤与多关键词 `|`。先搜唯一标识（符号名、常量名、错误文案、路由路径），不要先搜 `get`、`update`、`handler` 这类通用词。
3. **结构化定位**：若环境提供 AST / 符号 / 代码图谱类工具，优先于第 2 步——
   - 结构搜索按语法模式匹配节点（如 `function $NAME($$$)`、`class $C extends $B`），比纯文本正则准，且天然跳过注释与字符串里的假命中。
   - 符号与关系查询：先查定义，再查 callers / callees / impact。注意动态派发（反射、字符串调用、事件注册、依赖注入）可能漏边，此时回退到文本搜索交叉确认。
4. **看骨架再读正文**：大文件先用大纲/符号提取（ast_outline 类）拿到顶层定义与行号，再定点读；**不要**为了找一个函数而整读 1000 行以上的文件。
5. **定点读取**：读命中区域前后约 30 行，或读该文件的类型定义 / 导出签名 / 已有测试。类型定义与测试通常比实现本身更便宜，且更接近「规格」。
6. **追链**：追一个符号时逐层确认（定义 → 调用点 → 再上一层），每层只读需要的片段，不要批量读所有候选文件。

## 硬性预算（默认值；按任务规模上调时说明原因）
- 一次调研默认不超过 12 次检索/读取调用；明显超出说明问题没有收敛，先缩小范围。
- 不整读超过 400 行的文件（用大纲 + 定点读替代）。
- 不把整目录内容读进上下文；不重复读同一文件的同一区域。
- 跨包、跨仓库的大范围排查用子代理隔离上下文，只回收结论，不回收原始文件内容。

## 产出（调研结束即给方案，不写长文档）
改动方案
- 落点：文件:行 —— 现状是什么
- 改法：最小改动是什么，复用哪些既有函数/类型/组件
- 影响：调用点、兼容性、是否需要同步 i18n / 文档 / schema / 版本号
- 不做什么：明确排除的重构与顺带修改

方案默认直接执行，不等用户批准——除非命中高风险变更（鉴权、数据库 schema、破坏性迁移、公开 API、数据删除）。

## 反模式
- 收到需求立刻改代码，改完才发现落点错了。
- 先用递归列目录「整体了解一下结构」。
- 用整读文件的方式找函数。
- 为一个局部改动顺带重构无关模块。
- 只搜索不确认：命中结果没读上下文就断言「改这里」。
