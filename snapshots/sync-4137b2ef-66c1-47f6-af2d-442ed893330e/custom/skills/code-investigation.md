# 代码调研（Investigate → Plan）

目标：**在改动前用最少的 token 找到正确的落点，并给出最小改动方案。**

本 Skill 只负责「怎么找、找到什么程度停、最后输出什么」。具体检索能力由环境提供的工具承担（文件搜索、AST/符号搜索、代码图谱、文件读取、终端）；不要假设某条命令一定存在，也不要在本 Skill 里重复实现工具用法。

## 何时使用
- 需求已明确，但不知道实现落在哪个文件/函数。
- 要改共享逻辑，需先确认有哪些调用点。
- 接手陌生模块、评估影响面、判断改动是否外溢。
- 用户说「先看看代码」「分析一下再改」。

## 何时跳过
- 明确的一行改动、改名、拼写或文案修正：直接改。
- 目标文件已在上下文中读过：直接改。
- 纯问答/解释：按需检索即可，不必产出改动方案。

## 检索阶梯（先按问题类型选层，再逐层收敛）

**选层**——同一个问题用错层，要多花好几倍调用：

| 问题类型 | 首选层 |
|---|---|
| 「X 在哪 / 谁调用了 X / 改 X 会波及什么」 | 代码图谱（该仓库已建索引时） |
| 「哪些地方符合某语法模式 / 这个文件的结构」 | AST 结构搜索 / 大纲 |
| 「某字符串、常量、文案、配置项在哪」 | 文本搜索（grep / ripgrep） |
| 「有哪些文件 / 目录」 | 文件名搜索（glob） |

**收敛**——每次只读收敛到的片段：

1. **图谱层**（若环境提供代码图谱工具）：先查一次索引状态。
   - 已建索引 →「区域理解」用一次自然语言探索（`codegraph_explore` 类），一次返回相关符号源码 + 调用链，通常顶好几次 grep + read；「精确定位」用符号查询 / 单符号视图；「关系」用 callers / callees / impact。
   - 未建索引 → **不要擅自建**（会在仓库里创建索引目录）；往下用 2/3/4 层，必要时问用户是否建。
   - 索引可能陈旧（刚改过代码）→ 先同步再查询，否则结论基于旧代码。
   - **查询无果就回退**，不要反复重试；动态派发（反射、字符串调用、事件注册、DI）本来就可能漏边，用文本搜索交叉确认。
2. **结构层**：按语法模式匹配节点（如 `function $NAME($$$)`、`class $C extends $B`），比正则准，且天然跳过注释与字符串里的假命中；大文件先用大纲拿到顶层定义与行号，再定点读。
3. **文本层**：内容搜索一次带上 include 过滤与多关键词 `|`。先搜唯一标识（符号名、常量名、错误文案、路由路径），不要先搜 `get`、`update`、`handler` 这类通用词。
4. **文件层**：按文件名/路径模式搜索。只有确定层级时才列目录，禁止递归列举整个仓库。
5. **定点读取**：读命中区域前后约 30 行，或读该文件的类型定义 / 导出签名 / 已有测试。类型定义与测试通常比实现本身更便宜，且更接近「规格」。
6. **追链**：追一个符号时逐层确认（定义 → 调用点 → 再上一层），每层只读需要的片段，不要批量读所有候选文件。

## 硬性预算（默认值；按任务规模上调时说明原因）
- 一次调研默认不超过 12 次检索/读取调用；明显超出说明问题没有收敛，先缩小范围。
- 不整读超过 400 行的文件（用大纲 + 定点读替代）。
- 不把整目录内容读进上下文；不重复读同一文件的同一区域。
- 跨包、跨仓库的大范围排查用子代理隔离上下文，只回收结论，不回收原始文件内容。

## 产出（调研结束即给方案，不写长文档）
改动方案
- 落点：文件:行 —— 现状是什么
- 改法：最小改动是什么，复用哪些既有函数/类型/组件
- 影响：调用点、兼容性、是否需要同步 i18n / 文档 / schema / 版本号
- 不做什么：明确排除的重构与顺带修改

方案默认直接执行，不等用户批准——除非命中高风险变更（鉴权、数据库 schema、破坏性迁移、公开 API、数据删除）。

## 反模式
- 收到需求立刻改代码，改完才发现落点错了。
- 先用递归列目录「整体了解一下结构」。
- 用整读文件的方式找函数。
- 为一个局部改动顺带重构无关模块。
- 只搜索不确认：命中结果没读上下文就断言「改这里」。
- 仓库已建索引却用多轮 grep 手工拼调用关系。
- 图谱 / AST 查询无果后反复重试，而不是回退到文本搜索。
