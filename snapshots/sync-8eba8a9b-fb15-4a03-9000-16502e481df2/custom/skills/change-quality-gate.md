# 改动质量门（Verify → Review）

目标：**在说「完成」之前，用项目真实具备的能力验证，并诚实标注没验证的部分。**

本 Skill 只规定顺序、降级策略、自审清单与报告口径；具体执行能力由环境提供（终端、类型检查器、构建工具、测试运行器、浏览器）。不要在本 Skill 里重复实现这些工具。

## 何时使用
- 任何改了代码的任务，交付前。
- 修完 bug，确认没有引入新问题。
- 用户说「验证一下」「确认没问题」「review 一下」。

## 何时跳过
- 纯文档 / 注释 / 文案改动：只需确认引用路径与格式没坏。
- 只读任务（分析、解释）：没有改动就没有质量门。

## 第 1 步：探测真实命令（禁止假设）
按顺序看：项目 AGENTS.md / README → package.json 的 scripts → Makefile / justfile / pyproject.toml / Cargo.toml / go.mod → CI 配置（如 .github/workflows）。
**只跑项目里确实存在的命令**；没有的不要自己造，也不要为了一次验证新引入测试框架或依赖。

## 第 2 步：验证阶梯（从便宜到贵，失败立即停下修）
1. **类型检查**（tsc --noEmit 等）：覆盖面最大、最便宜，永远优先。
2. **构建**：能抓出类型检查看不到的入口、配置与产物问题。
3. **Lint / 格式检查**：只在项目已配置时跑，且只针对改动文件，不要全仓 reformat。
4. **相关测试**：只跑覆盖改动范围的测试文件或用例；全量测试只在改到核心共享逻辑时才跑。若该仓库已建代码图谱，先用「受影响测试」类查询（`codegraph_affected` 类，传入本次改动的源文件）拿到清单再跑——比凭感觉挑测试准、比全量跑省，是「测试不全」项目最实际的补偿。
5. **运行时 / 手工检查**：必要时跑最小可复现路径（起服务、调一次命令、浏览器点一次关键流程），并留下证据（输出、截图）。

改动涉及 UI 时，另需对照仓库的 UI 规范自查：颜色/字体/间距是否走既有 token、是否重复造了已有组件、Hover/Focus/Disabled/Loading/Empty/Error 状态是否齐全、暗色模式是否可用、文案是否进了 i18n 字典。

验证通过后，若该仓库已建代码图谱，同步一次索引（`codegraph_sync` 类），否则后续查询会读到旧代码。

## 第 3 步：项目什么都没有时的降级（不能让流程卡死）
- 用语言级检查兜底，至少确认「能解析、能编译」：tsc --noEmit、node --check、python -m py_compile、cargo check、go build ./... 等。
- 至少执行一次最小冒烟：跑一次入口命令、导入一次模块、调用一次改动的函数。
- 仍然做不到时：读 diff 做静态自审（见第 4 步），并把结论标为 NOT VERIFIED。

## 第 4 步：自审清单（读 diff，不是读文档）
- **明显 bug**：边界（空/0/负/超长/并发）、错误分支、早退、异步未 await、资源未释放。
- **遗漏引用**：import 未加、类型未更新、常量或字段改名后仍有旧引用。
- **破坏既有行为**：既有调用方的预期、默认值、序列化格式、公开签名是否被改变。
- **类型问题**：any 掩盖、as 强转、非空断言、可选值当必选使用。
- **改了不必要的文件**：范围外文件、格式漂移、顺手重构、锁文件意外变动。
- **违反项目规则**：AGENTS.md 的硬约束、目录分层、样式与 i18n 归属、文档同步要求。
- **遗漏同步项**：多处版本号、契约 / schema 文档、变更日志、需要重新生成的产物。

发现问题当场修，不要先汇报再等指令。

## 第 5 步：报告口径
对每个要求或改动项只给三种结论：
- **PASS**：已实现且有验证依据（写出具体命令与结果）。
- **FAIL**：未完成或验证失败（写出错误与原因）。
- **NOT VERIFIED**：实现可能完成但当前无法验证（写出为什么、已经验了什么、用户可以怎么接着验）。

禁止：把 NOT VERIFIED 说成 PASS；把「没跑过」说成「看起来没问题」；为了让检查通过而放宽或注释掉检查项。
